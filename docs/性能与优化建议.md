# 轻量 OA 系统 — 性能与优化建议（技术深挖）

> 版本：v3.0 ｜ 日期：2026-10-10 ｜ 面向**后续升级改造**
> 配套：《系统设计文档.md》《技术实现文档.md》《功能详解文档.md》《接口说明文档.md》
> 范围：基于当前 v3 代码逐文件核查，聚焦 **并发与锁、数据库/查询性能、数据处理与一致性、实时通信、文件存储、鉴权、前端与运维**。
> 每条给出「现象 → 定位（文件:行）→ 影响 → 建议」，末尾汇总优先级路线图与速查表。

---

## 0. 阅读指引与优先级定义

| 级别 | 含义 | 处理时机 |
|---|---|---|
| **P0** | 功能正确性/数据一致性受损，或高并发下明显错误 | 立即修复 |
| **P1** | 特定场景（广播、大目录、并发提交）下性能/体验劣化 | 下个迭代 |
| **P2** | 规模化/多节点部署才会暴露，或体验优化 | 按需演进 |

> 术语：**N+1** 指一次列表查询后，对每行再发额外查询；**CAS** 指带状态条件的更新（`UPDATE ... WHERE status=?` 并检查影响行数）；**游标分页**指按 `id > lastId` 翻页，替代 `LIMIT offset`。

当前系统定位「中小企业轻量版、单节点部署」，多数问题在**数据量小、并发低**时可接受；本文用于**升级前**的系统性排雷。

## 1. 并发与锁（重点）

> 现状：业务侧**几乎没有显式加锁**，全靠「先查后改」+ 少量数据库唯一约束。单用户低频操作下无碍，一旦出现**重复点击、多标签、并发请求**即可能出错。以下按风险排序。

### 1.1 审批任务并发处理（P0）

- **现象**：同一 `flow_task` 被两个并发请求同时「同意/驳回/转办」，两次都通过校验并各自推进流程。
- **定位**：
  - `mapper/FlowTaskMapper.xml:58` `updateHandle` → `UPDATE flow_task SET status=... WHERE task_id=?`，**未带 `AND status='PENDING'`**；
  - `service/impl/FlowInstanceServiceImpl.java:208 / 222 / 241` 先 `requireMinePending`（读→判 PENDING），再 `updateHandle`（无条件更新）。
- **影响**：重复审批意见、**下一节点任务被重复创建**、审批人收到重复待办；若为末节点，`finishApproved` 可能被执行两次，**考勤联动重复生成**。
- **建议**：
  1. 把状态判断下沉到 SQL 做 **CAS**：`UPDATE flow_task SET status=#{status},... WHERE task_id=#{taskId} AND status='PENDING'`，并检查返回行数 `==1`，否则抛「任务已被处理」；
  2. 或 `SELECT ... FOR UPDATE` 锁行后再判定（需在同一事务内）；
  3. 客户端按钮加幂等（提交后置灰 + 请求 `Idempotency-Key`）。

### 1.2 审批实例状态无 CAS（P1）

- **现象**：`withdraw`（撤回）与 `approve`（同意）并发时，两者都读到 `APPROVING`，随后实例状态被后写覆盖。
- **定位**：`FlowInstanceServiceImpl.java:190`（withdraw）与 `:208`（approve）均读校验 `ST_APPROVING`，但 `instanceMapper.updateStatus` 为无条件更新。
- **影响**：可能出现「已通过的流程又被撤回」或反之，`current_node_id` 与任务状态不一致。
- **建议**：`updateStatus` 增加 `AND status='APPROVING'` 的条件与行数校验；对末节点完成尤为关键。

### 1.3 考勤打卡 select-then-insert 竞态（P1）

- **现象**：同一员工并发/快速连点「上班卡」，两个请求都 `selectByEmpAndDate` 得到空，随后都 `insert`。
- **定位**：`service/impl/AttendanceServiceImpl.java:112`（punch）与 `:321`（upsert）先查再插；`att_record` 有 `UNIQUE KEY uk_att_date(emp_id, record_date)`（`docs/sql/oa_system.sql:327`）。
- **影响**：第二个 insert 触发 `DuplicateKeyException` → 未捕获 → 前端 500。唯一约束**保住了数据**，但错误未优雅处理。
- **建议**：捕获 `DuplicateKeyException` → 回退为 `update`（或改 `INSERT ... ON DUPLICATE KEY UPDATE`）；`punch`/`upsert` 补 `@Transactional`。

### 1.4 单聊会话并发创建（P2）

- **现象**：双方几乎同时点「发消息」，两个请求都 `selectBySingleKey` 为空，随后各自 `insert`。
- **定位**：`service/impl/ChatServiceImpl.java:71`（openConversation 单聊分支）先查后插；`chat_conversation.single_key` 有 `UNIQUE KEY uk_chat_single`（`docs/sql/oa_v3_upgrade.sql:49`）。
- **影响**：同上，唯一键阻止脏数据，但异常未处理返回 500。
- **建议**：捕获 `DuplicateKeyException` → 回查 `selectBySingleKey` 返回既有会话（幂等打开）。

### 1.5 事务边界与回滚语义（P1）

- **现象 a**：`AttendanceServiceImpl.saveRule:64`、`punch:112` **无 `@Transactional`**，其中 `insert` + `updateEnabled`（关旧规则）非原子，中途失败会留下「两条规则都启用/都不启用」的中间态。
- **现象 b**：`FlowInstanceServiceImpl.finishApproved:313` 用 `try/catch` 包住考勤联动（`FlowAttendanceNotifier.onApproved` 自身 `@Transactional`）。内部事务抛异常被外层吞掉后，**外层事务可能已被标记 rollback-only**，导致最终 `commit` 抛 `UnexpectedRollbackException`，整个审批回滚。
- **建议**：a) 补 `@Transactional`；b) 考勤联动改为**事务提交后异步执行**（`TransactionSynchronization` / `@TransactionalEventListener(AFTER_COMMIT)` / 消息队列），失败记录补偿日志，不再与主流程强绑定。

### 1.6 聊天推送在事务内（P2，一致性）

- **现象**：`ChatServiceImpl.send:137` 在 `@Transactional` 内落库后立即 `push`（`:165` → `:180`）。消息经 WebSocket 先到达客户端，而数据库事务可能尚未提交。
- **影响**：接收方收到实时消息后立刻刷新历史，可能查不到该条（读到旧快照）；若事务随后回滚，则出现「幽灵消息」。
- **建议**：推送放到**提交后**（`AFTER_COMMIT` 回调 / 事件）再发；或接受最终一致并在前端做乐观插入+去重。

### 1.7 缺少分布式锁与幂等（P2，演进方向）

- 当前无 Redis/DB 锁，无全局请求幂等键。**多实例部署**时 1.1–1.4 的竞态将进一步放大。
- **建议**：引入 Redis（`SETNX`/Redisson）做关键业务分布式锁；对「提交/审批/打卡」接口引入幂等键；或统一以数据库 CAS + 唯一约束兜底（成本最低，优先）。

## 2. 数据库与查询性能

### 2.1 列表查询 N+1（P1）

| 位置 | 问题 | 建议 |
|---|---|---|
| `ChatServiceImpl.java:54` myConversations | 每个会话：1×`selectByConversation`（取对端）+ 1~2×`userName`（user+emp）→ **约 3N 查询** | 一次性批量取会话成员与用户名称（`IN` 查询 + 内存 Map 组装） |
| `ChatConversationMapper.xml:31` selectByUser | 每会话 2 个相关子查询（`last_content`、`unread_count`） | 会话数可控可接受；量大时改「会话表冗余 last_content」或批量聚合 |
| `NoticeServiceImpl.java:218` broadcastNotice + `MessageServiceImpl.java:41` sendBatch | 逐接收人单条 `insert`，且每条 `send` 调 `configService.messagePushEnabled()`（再查库）→ **约 2N 次 DB 往返** | 批量插入（`<foreach>` 一条 INSERT）+ 配置项**本地缓存** |
| `FlowInstanceServiceImpl.java:342` resolveApprover | 候选审批人逐个 `userMapper.selectById` 判启用 | 一次 `IN` 查询取启用集合 |
| `FlowInstanceServiceImpl.java:156` detail | `taskMapper.selectByInstance` 被**调用两次**（:174 与 :177） | 取一次复用 |
| `EmpEmployeeMapper.xml:67` selectActiveList | 每行相关子查询取 `user_id` | 改 `LEFT JOIN sys_user`（v3 已修通讯录 `userId=null` 之痛，可再优化取法） |
| `ContactsServiceImpl.java:29/62` tree/query | 全量加载员工后在**内存**过滤/建树（无 SQL 分页/条件） | 大组织改服务端分页 + 条件查询 |
| `AttendanceServiceImpl.java:200` monthlyReport | 全量在职员工 + 全月记录内存聚合 | 组织大时改聚合 SQL/分页 |
| `NoticeServiceImpl.java:152` readStats | 未读名单用 `List.contains` 在 stream 内判断 → **O(n²)** | 用 `Set` 差集 |

### 2.2 文档目录权限链 N+1（P1）

- **现象**：渲染目录树时，对**每个目录**调用 `canRead`+`canEdit`，而 `checkPerm`（`DocServiceImpl.java:322`）**沿父链每层**执行 `selectByFolder` + `selectById`。
- **影响**：`O(目录数 × 层级 × 2)` 查询。100 个目录、3 层即约 600 次查询，仅为了画一棵树。
- **建议**：一次性加载**全部** `doc_folder` 与 `doc_folder_perm`，在内存里自顶向下**逐层传播**权限位（父→子继承），把链路查询降为常数次。

### 2.3 分页正确性与深翻页

- **文档检索分页失真（P1）**：`DocServiceImpl.java:166` `search` 先 `PageHelper.startPage` 分页 SQL，再在 Java 里 `filter(canRead)`。被过滤掉的行使**每页实际返回条数 < pageSize**，`total` 也偏大 → 分页错乱。
  **建议**：把可读目录集合先算出来，作为 SQL 的 `IN` 条件下推到查询，再分页。
- **聊天 offset 深翻页（P2）**：`ChatMessageMapper.xml:11` `ORDER BY msg_id DESC` + PageHelper `LIMIT offset`。消息量大时翻到深处线性变慢。
  **建议**：改**游标分页**（`WHERE conversation_id=? AND msg_id < #{lastMsgId} ORDER BY msg_id DESC LIMIT n`），前端「加载更早」。

### 2.4 索引总体评估（良好，个别补强）

已建索引基本覆盖热点查询：

- `flow_task(assignee_user_id, status)`、`flow_instance(applicant_user_id/status/def_id)`、`att_record(emp_id, record_date)`、`sys_message(receiver_user_id, is_read)`、`chat_message(conversation_id, msg_id)`、`chat_conversation_member(conversation_id, user_id)`、`doc_file(folder_id, name)`、`sys_op_log(user_id/time/type)`。
- 可补强：`sys_user(role)`（`selectUserIdsByRole` 现为全表扫描，表小可暂缓）；`flow_comment(instance_id)` 已有。
- **增长型大表**（`chat_message`、`sys_message`、`sys_op_log`、`att_record`）**无分区/归档策略**，长期将膨胀。建议按时间分区或冷热归档（P2）。

## 3. 数据处理与一致性

### 3.1 v3 请假考勤联动失效（P0，需优先修复）

- **现象**：请假审批通过后**不再生成考勤 `LEAVE` 记录**（联动静默失败）。
- **根因**：v3 将请假 `begin_date/end_date` 字段类型改为 `DATETIME`，前端 `FlowStart.vue:208` 以 `value-format="YYYY-MM-DD HH:mm:ss"` 提交（如 `2026-10-10 09:00:00`）；而 `AttendanceServiceImpl.java:385` `parseDate` 用 `LocalDate.parse(...)` 解析 → 抛 `DateTimeParseException` → `catch` 返回 `null` → `onApproved:292` 判定起止为 null，**跳过联动**。
- **影响**：v2 正常的「请假 → 考勤」联动在 v3 静默失效，且**无任何报错**（被 catch 吞掉），属功能回归。
- **建议**：
  1. `parseDate` 兼容 `yyyy-MM-dd HH:mm:ss`（先按 DATETIME 解析再取 `toLocalDate()`，或在 `options` 中显式声明格式）；
  2. 起止改为 DATETIME 后，请假「天数」口径需重新定义（跨半天/按小时），考勤联动按**日期区间**生成 `LEAVE`，并对半天情形补充口径；
  3. 移除静默 catch，改为记录 warn 日志，便于发现同类问题。

### 3.2 文本解析强耦合（P1）

- **现象**：加班时长的读取依赖对 `remark` 文本的**正则匹配**（`AttendanceServiceImpl.java:396` `parseOvertimeHours`，匹配「时长 X 小时」）。
- **影响**：文案一改即失效；报表加班小时统计口径脆弱。
- **建议**：加班时长以**结构化字段**落库（如 `att_record` 增 `hours DECIMAL` 或在 `form_data_json` 中直接取数值），报表读结构化值。

### 3.3 JSON 表单数据的模式与版本（P2）

- `flow_instance.form_data_json` 存 `{fieldKey: value}`，**无 schema、无版本号**；分支比较在 Java 里按运行时类型判断（`FlowInstanceServiceImpl.java:403` `branchMatch`）。
- **影响**：字段类型/口径变更（如 3.1 的 DATE→DATETIME）易引发隐性不兼容；跨版本回放历史单有风险。
- **建议**：`form_data_json` 内嵌 `_schemaVersion`；表单字段定义变更走「新版本表单」，历史实例保留其定义快照。

### 3.4 数值精度（P2）

- 时长/加班小时用 `double`（前端 `FlowStart.vue:70` 天=小时/24 取两位；后端 `parseOvertimeHours` double）。累计统计存在**浮点误差**。
- **建议**：金额/工时改用 `BigDecimal`（后端）与整数「分钟/秒」为基（前端），展示层再格式化。

### 3.5 逻辑删除与孤儿数据（P1）

- `DocServiceImpl.deleteFile:231` 只删当前文件实体并 `markDeleted`，**历史版本文件与行保留**；`doc_file` 逻辑删除行、磁盘版本文件长期累积。
- **建议**：提供清理策略（级联删除版本文件/行，或归档表），并加定时任务回收磁盘。

## 4. 实时通信扩展性

| 项 | 现状 | 影响 / 建议 |
|---|---|---|
| 消息代理 | `WebSocketConfig` 用**内存 `SimpleBroker`**（`/topic`、`/queue`） | **仅单节点**：多实例部署时 A 节点用户收不到 B 节点推送。改造：启用外部 STOMP broker（RabbitMQ/ActiveMQ relay）或引入 Redis pub/sub 广播（P2） |
| 推送方式 | `ChatServiceImpl.push:180` 循环对**每个成员** `convertAndSendToUser` | 群聊成员多时 O(M) 次发送；建议改为「会话频道 + 客户端订阅」为主，减少定向扇出 |
| 推送时机 | 在事务内推送（见 1.6） | 提交后推送 |
| 连接治理 | 无心跳、无消息大小上限、无发送频率限制；`setAllowedOriginPatterns("*")` | 补心跳/背压、单会话订阅上限、发送限流（防刷）；生产收敛跨域白名单（P1/P2） |
| 离线消息 | 无离线投递/漫游，靠 REST 拉历史 | 轻量可接受；如要「未读必达」需离线消息表 + 上线补投（P2） |
| 鉴权 | 仅 CONNECT 校验一次 | 长连接期间 token 过期不重校验；如需可加会话有效期与踢下线（P2） |

## 5. 文件与存储

- **本地磁盘单点**（`FileStorageServiceImpl`）：`oa.upload-dir` 本地目录，无对象存储/CDN；多实例部署时文件不共享。**建议**：抽 `FileStorageService` 接口（已具备）→ 增加 OSS/S3/MinIO 实现（P2）。
- **DB 与磁盘非同一事务**：先写盘（`store`）后写库（`doc_file`/`sys_attachment`），任一步失败可能留**孤儿文件**或**悬空记录**。**建议**：写盘成功后再落库，失败回滚删盘；或引入「临时区 + 提交确认」两阶段（P1）。
- **无缩略图/去重**：头像与大图原样存储；相同文件重复占盘。**建议**：图片生成缩略图、按内容哈希去重（P2）。
- **大文件**：走应用内存（`MultipartFile`），注意与 `max-file-size`（50MB）配合的超时与内存；生产建议直传对象存储（P2）。

## 6. 鉴权与安全（性能/健壮性相关）

- **JWT 无吊销/黑名单**：登出仅前端清 Token（`JwtInterceptor`），令牌到期前始终有效。**建议**：引入 Redis 黑名单（按 `jti`）或短令牌 + 刷新令牌；至少对敏感操作二次校验（P1）。
- **每请求解析 Token**：`JwtInterceptor.preHandle` 每次 HMAC 校验，临界期还 `createToken` 续期。当前 QPS 下可接受；高并发可缓存解析结果（P2）。
- **无限流**：登录等接口无频率限制，存在暴力破解 / 刷接口风险。**建议**：网关/拦截器加基于 IP+账号的限流（P1）。
- **日志级别**：`application.yml` 将 `com.tianyu.oasystem.mapper` 设为 `debug`，**生产会打印每条 SQL 及参数**，显著影响吞吐与日志量。**建议**：生产改 `info`（P0/上线前必改）。

## 7. 前端性能

- **未读角标轮询**：`AdminLayout` 顶栏每 60s 轮询 `messages/unread-count`，多标签/多用户放大 DB 计数压力。**建议**：改用已有的 WebSocket `/user/queue` 推送未读变更，或降低频率/合并请求（P1）。
- **聊天已用 STOMP，其余仍轮询**：可统一到实时通道。
- **长列表未虚拟滚动**：消息历史、员工列表在数据量大时渲染卡顿。**建议**：`el-table` 虚拟滚动 / 消息窗口化（P2）。
- **头像 blob 拉取**：`UserAvatar.vue` 每人一次带权请求，列表页会放大请求数。**建议**：内存缓存 blob URL、`Cache-Control` + ETag（P1）。

## 8. 架构与运维

- **无缓存层**：`ConfigServiceImpl` 每次 `getValue` 查库（热点：消息推送开关）；无 Redis。**建议**：加进程内缓存（Caffeine）或 Redis，配置变更时失效（P1）。
- **无异步/队列**：公告广播、考勤联动、消息落库等可在**请求线程内同步完成**，发布大公告会阻塞请求。**建议**：引入线程池/消息队列异步化这些「旁路」动作（P2）。
- **连接池未显式调优**：默认 HikariCP（`maximum-pool-size`≈10）。高并发需按负载调参，并设置**事务/查询超时**（P1）。
- **无监控/链路追踪/慢 SQL 告警**：仅文件日志。**建议**：接 APM（如 Spring Boot Actuator + Micrometer）、开启慢查询日志（P2）。
- **无读写分离/分库分表**：单库单表，中小企业足够；规模化再评估。

## 9. 改造优先级路线图

### 第一批（P0，立即）
1. **修复 v3 请假考勤联动失效**（§3.1）：`parseDate` 兼容 DATETIME，口径重定义，去除静默 catch。
2. **审批任务 CAS 加锁**（§1.1）：`updateHandle` 带 `AND status='PENDING'` + 行数校验。
3. **生产日志级别**（§6）：`mapper` 由 `debug` 改 `info`。

### 第二批（P1，下个迭代）
4. 审批实例状态 CAS（§1.2）、打卡/单聊并发唯一键异常兜底（§1.3/1.4）。
